Policies and concurrency
------------------------

Invitation secrets use 32 random bytes; only uppercase SHA-256 token hashes are persisted. The 48-hour boundary is exclusive: `now >= ExpiresAt` is invalid. Accepted/revoked invitations and replaced tokens are invalid. A filtered unique `(OrganizationId, NormalizedEmail)` index allows one pending invitation, including an expired row until a new issue retires it. Reissue marks the previous pending row revoked before inserting the replacement, within one transaction. Rows include inviter, membership role, creation/expiry/acceptance/revocation/delivery timestamps and SQL Server row version.

Creation, revocation, and acceptance use serializable transactions and the existing `OrganizationWriteLock` (UPDLOCK/HOLDLOCK), shared with organization administration, instructor assignment, and enrollment guards. Acceptance rechecks active organization and current stored inviter authority inside that transaction. Revoked inviter authority denies acceptance. A transaction-owned SQL Server application lock on a SHA-256 normalized-email resource serializes acceptance/account creation and exact-email membership assignment across organizations. The same lock is added to the existing exact-email membership assignment workflow. Reset also acquires this email lock, serializing competing reset attempts. Negative lock results fail safely; there is no automatic replay.

Existing exact-email ambiguity (Identity EmailIndex is not unique) is denied rather than selecting an arbitrary account. No destructive unique-email change or account merging is attempted. Existing accounts require authenticated matching user ID, matching normalized email, and stored `EmailConfirmed`; global SuperAdmin accounts use the established membership workflow. New accounts use Identity password validation and begin unconfirmed. Identity account creation, membership creation, email confirmation, and invitation consumption share the same EF context and transaction. Email confirmation occurs only in successful acceptance. An existing matching membership consumes the invitation successfully; a conflicting role fails without overwriting it and directs the administrator to role change. No assignment, quiz, enrollment, completion, or last-Admin safeguards are relaxed.

Password recovery uses Identity's DataProtectorTokenProvider with a one-hour lifetime. Password reset validates the token and Identity password policy and rotates the security stamp. Reusing any pre-reset reset token fails. Every newly issued JWT carries `lms-stamp`; JWT validation compares it against the current stored stamp. All legacy JWTs without that claim fail after deploying this validation, so require fresh login. Existing web sessions hold their JWT server-side; cookie validation calls `/api/account/session` on every request and removes/rejects sessions whose JWT fails. This is logical revocation across web instances; already cached session data may remain until next use/expiry. Requests already authorized before a reset cannot be recalled. Recovery never signs a user in or changes existing email confirmation.

Token-bearing MVC pages use no-store, no-referrer and CSP `default-src 'none'` with only same-origin styles/forms. They render without the shared layout, scripts, analytics, iframes or external resources. All displayed fields/messages are Razor encoded. Password inputs have no value attribute and passwords are cleared on failures. A protected random HttpOnly Secure host-cookie identifies an encrypted server-memory link session, separated by purpose, for 20 minutes. Refresh/restart/expiry loses that session; reopening the original email link establishes another without consuming it. Sticky routing is needed for the current memory session architecture. No sensitive token is included in redirects. The original emailed URL necessarily contains its token until the initial GET redirects.

API recovery is limited to five requests/minute per observed IP, zero queue; web account pages reuse the existing ten/minute login policy, and administration reuses ten/minute per authenticated user. Session validation is deliberately outside recovery limits. Behind the MVC server, API recovery requests share that server's observed IP; size traffic limits accordingly before deployment. New account API/MVC bodies are capped at 16 KiB and password inputs at 1024 characters. Uniform forgot responses prevent response-body/status enumeration; delivery latency is not guaranteed identical and should be assessed with the chosen provider. Use deployment-level abuse protection for distributed attacks and multi-instance limits.

Delivery and recovery
---------------------

`IAccountEmailSender` is the delivery boundary. Development registers `DevelopmentAccountEmailSender`; non-Development registers `UnconfiguredAccountEmailSender`, which explicitly refuses delivery. There is no production provider, paid service, new NuGet package, or public capture endpoint. Production email is a deployment blocker until an explicit provider implementation and its configuration are supplied and registered. Setting a public URL alone does not configure email. The API can still authenticate existing accounts; an invitation send fails explicitly (503), and forgot-password retains its generic response while logging a generic delivery failure. No production fallback to capture is permitted.

Invitations use a documented recoverable delivery workflow rather than an outbox containing raw secrets. Commit the invitation with `DeliveredAt=null`, then send, then record delivery after sender success. Email and database are not atomic. A send failure/crash leaves the row discoverable. If a successful send is followed by a failed database acknowledgement, delivery remains uncertain; do not automatically retry. The list shows `Unconfirmed`, not `Delivered`. Sender success indicates acceptance by the configured delivery boundary, not guaranteed inbox receipt. Development success means a private capture file was completed.

Administrators recover by reading the list, confirming the state and intended recipient/role, then explicitly reissuing if necessary. This always generates a new secret and invalidates the previous pending invitation; lost raw tokens cannot be retrieved from the database. A user with an ambiguous acceptance outcome checks their organization list; the administrator inspects AcceptedAt before further action. An ambiguous reset outcome is recovered by sign-in or a new recovery email, without replaying the prior submission. MVC network/timeout/JSON failures produce these recovery instructions; there is no automatic mutation retry. API callers must follow the same procedure after an uncertain response.

Development captures live under `LMS.Api/App_Data/PrivateEmails/`, outside wwwroot. Filenames are generated GUIDs; files contain recipient addresses and sensitive links. Writes use a temporary file then rename. Windows directory ACLs restrict access to the service identity; Unix mode is owner-only, with owner-only capture files. Permission failures fail delivery. Access files privately as that local identity; never copy them to public directories, tickets, screenshots, logs, or shared artifacts. Delete captures after each development test session and retain no longer than 72 hours. This is an operator retention policy, not an automatic cleanup job. Expired links still contain personal data. The directory is excluded from Git and API content/None publication. Existing files from older permissions must be reviewed separately by an authorized operator.

Configuration and deployment prerequisites
------------------------------------------

| Setting | Requirement |
|---|---|
| `AccountLinks:PublicUrl` / `AccountLinks__PublicUrl` | Explicit trusted HTTPS MVC origin with `/` path and no credentials/query/fragment. Development defaults to `https://localhost:7207/` from the existing HTTPS launch profile. No request Host header is used. Configure the actual production origin. |
| `ASPNETCORE_ENVIRONMENT` | `Development` enables private capture; all other environments refuse unconfigured delivery. Never run public production deployments as Development. |
| `LmsApi:BaseUrl` | Existing trusted HTTPS API origin used by the MVC client; redirects disabled and HTTP client loggers removed. |
| `Jwt:Key`, `Jwt:Issuer`, `Jwt:Audience`, `Jwt:AccessTokenMinutes` | Existing JWT settings, no secrets added. Configure secure production values; legacy JWTs require fresh login. |
| Data Protection key storage | Existing framework configuration; persist and protect API keys across restarts/instances for valid reset tokens. Web keys and server sessions follow existing hosting/session constraints. |
| Production email provider | Register an explicit `IAccountEmailSender` implementation in place of the refusal sender and supply that provider's own configuration privately. No provider-specific key names or secrets are invented here. |

Exclude account-link query strings and bodies, passwords, reset/invitation tokens and Authorization headers from reverse-proxy access logs, tracing, APM, analytics, WAF captures and support diagnostics. Application Hosting.Diagnostics and MVC logs are filtered at Warning to prevent informational request URL and detailed binding logs; API HttpClient loggers are removed. Do not enable EF sensitive-data logging or HTTP body logging. Upstream logs cannot be controlled by this code.

Its Down drops only that new table (data loss if used). Deployment requires separate authorization, schema-chain review, backups, and application of the pending prerequisites. Build/model checks do not establish database migration state.

SQL Server must support/permit transaction-owned `sp_getapplock`; verify lock/deadlock/timeout behavior and actual index plans in an authorized disposable environment before deployment. Unique constraints and row version are modeled but their runtime race handling is not proven here. Simultaneous conflicting writes fail safely and are not automatically retried. The Infrastructure project adds a shared-framework reference for existing ASP.NET Identity/Data Protection/web utilities; it uses cached dependencies and adds no packages. This exposes three NU1510 warnings about already existing package references being redundant; those existing references are preserved.
